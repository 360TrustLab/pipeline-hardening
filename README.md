# CRH04: Hardening CI/CD Pipelines

I use this lab to examine the authority of a release, then ask what a team can
narrow without breaking legitimate deployment. The operating questions matter:
who maintains the role, who reviews a change, and who can recover the release?

See [Operating decisions](OPERATING_DECISIONS.md) for rollout, ownership, and
recovery questions. The runnable checks and the AWS validation path remain
separate.

Conference demos for Guillermo A. Fisher, Live! 360 Orlando 2026.

## Run locally (no installation or AWS required)

```sh
python3 -m unittest discover -s tests -v
python3 lab.py
```

`artifacts/report.json` is generated by the local condition model. It demonstrates
how an exact protected-environment subject excludes a branch and sibling repo.
The claims use visibly synthetic IDs. This is not authentication, an IAM simulator,
a successful STS exchange, or proof of AWS enforcement.

## Demo 1: inspect the trust chain (10–12 minutes)

1. Open `examples/overprivileged.yml.txt`. Compare its workflow scope and mutable action tag.
2. Open `.github/workflows/deploy.yml`: scoped job token, pinned actions, environment.
3. Compare local before/after subject decisions with `python3 lab.py`.
4. Open `infra/stack.json`: OIDC audience and exact subject, then one S3 prefix.

## Demo 2: harden and retest (10–12 minutes)

1. Configure the AWS sandbox as described below.
2. Run **Deploy one sandbox artifact** on `main`.
3. Show the intended `releases/` upload succeeds and `unrelated/` returns AccessDenied.
4. Review the run logs and the role policy. The local negative subject test is a
   condition illustration, not a real failed STS request from another repository.

## AWS setup (not automatic)

Use a dedicated sandbox. Existing GitHub OIDC provider must be supplied explicitly.
Inspect the real subject of this repository: new repositories can include immutable
owner/repository IDs. Do not paste a raw JWT into slides, issues, or logs.

```sh
aws --profile YOUR_SANDBOX cloudformation deploy \
  --stack-name live360-pipeline --template-file infra/stack.json \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides GitHubOidcProviderArn=YOUR_PROVIDER_ARN ExactGitHubSubject=YOUR_EXACT_SUBJECT
```

In GitHub create the `conference-sandbox` environment, restrict it to `main`,
configure a required reviewer if your plan supports it, and set environment
variables `AWS_ROLE_ARN`, `ARTIFACT_BUCKET`, `AWS_REGION`, `AWS_ACCOUNT_ID` from
stack outputs. `environment:` in YAML alone does not configure protection rules.
Cloud deployment is manual and unavailable until these variables exist.
The stack does not grant account-wide administration or create static access keys.

## Reset and teardown

Local reset: rerun `python3 lab.py` (deterministic fixtures). Remove only this
stack's test object before deleting the stack; use the bucket returned by stack
outputs, never an account-wide cleanup command. Objects expire after one day.
Delete `live360-pipeline` using the same explicit sandbox profile. Remove the
GitHub environment when the conference is over if it is no longer needed.
